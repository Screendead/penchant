The 10 min goal is not met. On GitHub's standard Mac runner, 13–18 min goes by before the first test runs. The tests now take 5 min.

Where a run's 20–26 min go now

setup 3

job, Flutter SDK and caches simulator's first boot (heavy disk use; slows whatever runs beside it) Flutter's work before Xcode Xcode build, cached 24 tests

What this PR fixed: the iOS build cache missed build/ios, so every run cloned firebase-ios-sdk again (8.5 min). Booting the simulator during the cache downloads made them up to 5× slower. A fresh checkout made Xcode treat every file as changed. Runner speed alone moves a run by ±3 min.

Call: how far to go for 10 minutes

A. Merge #218 and stop here Recommended

The result arrives in about 23 min, not 31.5, and the Mac job stops taking 100 min. It's free and already built.

Cost noneRisk lowEffort done

B. Split the tests over two runners

Each runner still pays the full setup, so this saves about 2.5 min (to roughly 18–23). It uses twice the runner time, which is free while the repo is public.

Cost freeRisk lowEffort ~1 h

C. GitHub's larger paid Mac runners

More cores and faster disks. My guess is 30–40% faster, but that is unmeasured, so 10 min isn't certain. Billed per minute; it needs a payment method on the account.

Cost per run, paidRisk unmeasuredEffort ~1 h + billing

D. A dedicated Mac as a self-hosted runner (not your Mac)

The simulator stays booted and the build stays warm, so a run would probably take 7–9 min (inferred: build about 1 min plus 5 min of tests). It needs hardware and upkeep. e2e never runs on PRs, which limits the risk of a self-hosted runner on a public repo.

Cost a Mac miniRisk upkeepEffort half a day

Why A: the 10 min target needs money or hardware. B is cheap but saves only about 2 min. If 10 min matters, D is the one option likely to reach it.
